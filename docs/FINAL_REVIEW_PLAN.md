# [PLAN-FR1] 보강 연구계획서의 최종 검토 기획

- 개정일: 2026-10-01 (KST)
- 승인 범위: 대표와의 대화에서 정한 사용자 흐름과 기획서 업데이트. 이번 작업은 문서 개정이며 제품 구현·릴리스·실제 API 실행은 포함하지 않는다.
- 상태: **신규 최종 검토 단계는 구현 예정**. 기존 수정 권고 서버·조립 기능은 개발 브랜치/통합 후보에 있고, 수정본 뷰어는 별도 UI 브랜치에 있다. main 병합·제품 연결·검증 상태는 HANDOFF를 따른다.
- 우선순위: 현재 수정 권고와 조립·UI 연결의 완료 이후 적용한다. 이번 개정으로 기존 릴리스 태그나 마감 일정을 자동 변경하지 않는다.

## 1. 결과물과 제품 목적

Neumann은 초안의 모호함과 설계 결함을 실제 평가이력에 연결하고, 연구자의 판단을 반영해 보강된 연구계획서 한 부를 만든다. 목표는 심사에서 반려나 반복 보완의 원인이 될 수 있는 결함을 사전에 줄이는 것이다. 반려 확률 수치, 선정 보장, 완벽한 과학적 설계라는 보증은 출력하지 않는다.

실제 심사에서 드러난 문제와 저자 대응 기록은 적용 조건을 따져 재사용한다. 심사 지적, 거절, 연구 실패를 동일한 사실로 취급하지 않는다. 이전 연구의 맥락을 현재 계획에 적용한 이유가 설명돼야 하며, 채택된 연구의 대응을 참고해도 그것이 채택 원인이었다고 단정하지 않는다.

최종 산출은 검토한 계획서, 변경 이력, 수정 근거, 남은 쟁점과 구현 경로·검증 결과다. 연구자의 수정 확정 한 번으로 문안 검토와 구현 조건 점검을 수행하고, 자료와 승인된 실행 범위가 있으면 최소 실행 검증까지 묶어 반환한다. 공고 적합성 서비스, 성장 주제 추천, 별도 실험 이력 플랫폼은 이번 범위에 넣지 않는다.

## 2. 사용자 여정

| 순서 | 사용자 또는 서비스의 행동 | 다음으로 넘기는 결과 |
|---|---|---|
| 1 | 연구자가 연구계획 초안을 입력한다 | 분석 대상 초안 |
| 2 | 서비스가 리스크, 해석, 적용 이유와 근거를 제시하고 보강안을 만든다 | 리스크 목록과 수정 제안 |
| 3 | 연구자가 제안을 채택·직접 수정·기각하고 수정 확정·검증을 누른다. 실행 가능한 경우 같은 화면에서 사전 범위를 확인하고 실행 포함을 선택한다 | 고정된 보강안과 검증 범위 |
| 4 | 서비스가 문안 검토 1회와 구현 조건 점검, 준비·승인된 경우 최소 실행 검증을 수행한다 | 단계별 관찰·미해결·실행 상태 |
| 5 | 서비스가 계획서와 변경 이력·검토·구현 경로·검증 결과를 한 묶음으로 반환하고 종료한다 | 연구자가 확인할 최종 결과. 추가 수정은 별도 요청 |

3단계의 확정은 연구자 문안과 검증 범위의 고정이며, 심사 통과나 무결함 판정이 아니다. 필수적인 두 번째 확정이나 별도 검증 요청 화면은 두지 않는다. 문제를 발견한 검토도 결과를 반환하고 종료한다. 검토 과정에서 연구자 문안을 자동으로 바꾸지 않는다.

## 3. 입력을 고정하는 기준

문안 검토와 구현 조건 검증은 다음 자료를 하나의 제출 묶음으로 받는다.

- 분석에 사용한 원본 계획과 식별값.
- 기존 리스크 및 해당 리스크의 검증된 근거.
- 수정 권고, 수정 이유와 대상 줄, 연구자의 결정.
- 조립된 보강안과 변경 내역, 미결·충돌·확인 필요 항목.
- 실행을 포함하는 경우 선택된 핵심 가정·자료·방법·측정/판정 기준·명령 규격·자원 상한과 연구자의 승인. 자료가 없거나 실행을 선택하지 않으면 구현 경로와 필요 자료를 반환하고 실행은 미실행으로 표시한다.

보강안의 식별값을 검토 기록에 연결한다. 검토 뒤 문안이 달라지면 이전 결과는 이전 문안의 검토로 남기고, 현재 문안은 `검토 후 변경됨`으로 표시한다. 다른 계획서나 다른 리스크의 결과를 현재 문안의 검토로 재사용하지 않는다. 서명·근거 출처 확인은 기존 기능을 확장하며, 계약 변경은 PM 승인 후 추가한다.

## 4. 검토 범위

문안 검토 범위는 변경한 부분, 그 부분과 연결된 기존 지적, 일관성을 판단하는 데 필요한 문맥이다. 필요한 경우 제출된 계획서 전체를 문맥으로 읽을 수 있으나, 전체 검색·리스크 생성 파이프라인을 다시 실행하지 않는다. 새 데이터 수집이나 자동 검색 확대도 이 작업에서 수행하지 않는다. 같은 작업의 구현 조건 점검과 승인된 최소 실행 검증은 §10의 명세를 따른다.

| 검토 항목 | 확인할 내용 | 항목별 결과 |
|---|---|---|
| 기존 지적의 반영 | 필요한 방법·데이터·평가 조건이 문안에 실질적으로 들어갔는가 | 해결 / 미해결 / 판단 보류 |
| 근거와 수정 이유 | 현재 수정 이유가 해당 근거의 내용과 적용 맥락을 벗어나지 않는가 | 확인 / 불일치 / 판단 보류 |
| 변경으로 생긴 문제 | 수정문이 관련 목표·방법·데이터·평가·일정과 충돌하거나 미확인 사실을 단정하지 않는가 | 문제 발견 / 검토 범위 내 문제 미발견 / 판단 보류 |
| 미완료 항목 | 미결정·충돌·확인 필요 자리표시가 남아 있는가 | 항목과 대상 위치를 명시 |

기각된 제안은 적용되지 않은 것으로 센다. 원문에 해당 문제가 여전히 남아 있다면 미해결로 표시하되 기각만으로 계획 전체를 부적합 판정하지 않는다. 표현만 바뀌고 요구되는 검증 설계가 빠져 있다면 해결로 처리하지 않는다.

`문제 미발견`은 실제 검토한 범위의 관찰이다. 계획서 전체의 무결함이나 과학적 성과를 뜻하지 않는다. 의미 검토의 판단 근거는 원본과 보강안의 위치, 리스크 식별값, 사용한 발췌 번호로 연결한다. 인용문은 기존 원문 오프셋에서 코드가 구성한다.

## 5. 반복 상한과 문제 처리

- 한 제출 묶음의 최종 검토 실행은 **1회**다. 검토 안에서 자동 재수정·재검색·재검토 반복은 **0회**다.
- 입력 계약·계획 식별값·근거 대조·충돌·자리표시는 코드 검사로 확인하고, 의미 검토는 기존 제품 provider를 이용하는 한 번의 단계로 계획한다. 여러 항목을 검토하더라도 해결될 때까지 다시 생성하는 구조를 두지 않는다.
- 기존 serving의 자원·입력·시간 제한을 따른다. 제한 초과·모델 실패·응답 계약 위반은 `검토 미완료`로 반환한다. 의미 검토 실패를 규칙으로 성공 판정하지 않는다. 완료한 코드 검사는 의미 검토와 구분해 표시할 수 있다.
- 문제가 있는 수정은 확정 보류 항목으로 표시한다. 원문·수정문·문제 이유와 근거를 함께 보여준다. 연구자는 기각해 해당 부분의 원문을 유지하거나 직접 수정할 수 있다.
- 연구자가 요청하는 추가 AI 수정이나 재검토는 별도 작업이다. 시스템이 자동으로 시작하지 않는다. 직접 수정 뒤에도 이전 검토를 새 문안에 대한 확인으로 표시하지 않는다.
- 최종 판단권은 연구자에게 있다. 서비스가 임의로 원문을 덮어쓰거나 검토 실패를 근거로 계획 전체를 자동 반려하지 않는다.

종료 조건은 모든 리스크의 소멸이 아니라, 제출된 문안에 대해 제한된 검토를 끝내고 결과를 반환하는 것이다. 미해결·판단 보류가 남은 상태도 정직하게 반환하고 작업을 끝낸다.

## 6. 결과와 화면

반환할 계획서 본문은 제출한 문안과 같아야 한다. 검토 보고서는 다음을 포함한다.

- 검토 대상 원본/보강안 식별값, 검토 시각, 생성 방식·모델·버전, 검토 완료 여부와 실제 검사 범위.
- 기존 리스크별 해결·미해결·판단 보류 결과와 해당 위치·판단 이유·근거.
- 변경 부분과 관련 문맥에서 발견한 모순, 미확인 사실, 미결정·충돌·확인 필요 사항.
- 연구자가 채택하거나 직접 수정한 이력, 기각한 제안과 결정 이유.
- 검토 미완료 단계와 사유, 검토 후 문안이 바뀐 경우 그 상태.

UI의 주 행동은 `수정 확정·검증` 한 번이다. 수정 화면에서 구현·검증 범위와 실행 포함 선택을 제시하고, 결과 화면은 계획서·문안 검토·구현 경로·실행 상태를 함께 보여준다. 문안 검토·구현 조건 점검·실행의 내부 단계는 사용자에게 필수적인 별도 요청/확정으로 나누지 않는다. 실행 승인 없는 문안 확정만으로 도구 실행을 시작하지 않는다. 검토 중 버튼 연타나 요청 재전송은 같은 제출을 다시 실행하지 않도록 처리한다. 네트워크 재연결도 새 검토·실행을 자동으로 시작하지 않는다. 수정과 검토 기록을 내보내기에 연결하되, 재검토하지 않은 직접 수정본에는 이전 검토를 현재 문안의 보증처럼 붙이지 않는다.

`반려 확률 0%`, `심사 통과`, `완벽한 계획서` 같은 표시는 두지 않는다. 제품 설명은 반려 위험에 대비하도록 보강한다는 목표로 작성한다.

## 7. 구현 순서와 소유권

| 과제 | 담당 범위 | 착수 조건과 산출 |
|---|---|---|
| 계약·연결 설계 | PM(E0) | 수정 권고/조립/서명/UI의 실제 연결 상태 확인. 기존 계약을 유지한 추가 검토 계약과 식별값 정책 승인 |
| 최종 검토 단계 | E3 | 제출 묶음의 고정, 코드 검사와 의미 검토, 실패·판단 보류, 1회 실행 보장 |
| 확정·검증과 결과 UI/API | E4 | 단일 제출과 통합 결과, 실행 포함 선택·범위 승인, 중복 실행 방지, 오류·검토 후 변경 표시, 결과 내보내기 |
| 효과 평가 | E5 | 평가 규칙을 결과 보기 전에 정하고 원본/보강본을 독립 비교 |

이번 문서는 작업 배정이나 구현 완료를 뜻하지 않는다. 기존 v2 병합·독립 검증을 우선하며, 신규 기능은 구현·검증 후 별도 완료로 기록한다. 개발·단위 검증은 mock/offline, 제품 모델과 실제 API 확인은 AGENTS.md의 기존 승인·실행 규칙을 그대로 따른다.

## 8. 완료 기준과 필요한 반례

| 기준 | 검사할 시나리오와 기대 결과 |
|---|---|
| 같은 문안 검토 | 반환 본문이 제출한 보강안과 글자 단위로 같고 식별값이 일치 |
| 실질적인 지적 해소 | 방법·검증 조건을 실제 추가한 사례와 표현만 바꾼 사례를 구분 |
| 잘못된 수정 발견 | 알려진 모순·근거 불일치·지어낸 표본/성과·자리표시를 삽입한 사례가 해결 판정으로 통과하지 않음 |
| 불충분한 근거 | 판단 보류와 이유가 표시되고 해결 또는 문제 미발견으로 위장하지 않음 |
| 연구자 결정 보존 | 채택·직접 수정·기각·미결을 구분하고 기각/충돌 문안을 임의 적용하지 않음 |
| 종료와 중복 방지 | 문제 남음·버튼 연타·재전송·재연결에서도 자동 재수정·재검색 0회, 제출당 검토 1회 |
| 검토 실패 | 시간 초과·모델 실패·계약 위반에 검토 미완료가 화면과 내보내기에 표시 |
| 변경 뒤 검토 상태 | 검토 후 문안 변경은 식별값 불일치와 검토 후 변경 상태로 표시 |
| 근거 정직성 | 없는 id·다른 카드 근거·변조된 인용·맞지 않는 오프셋을 거절 |

위 표는 후속 구현의 완료 기준이며 이번 문서 개정에서 통과한 제품 테스트 목록이 아니다. 빌더와 다른 모델의 독립 검증 및 해당 변경의 verify 통과를 완료 조건으로 둔다.

## 9. 효과 주장과 측정

원본과 보강본의 순서·시스템 출처를 가린 독립 쌍비교로 보완 요구의 수·중요도, 설계의 실행 가능성, 새로 생긴 문제를 평가한다. 동일한 루브릭을 사용하고 표본 수·입력 범위·평가자·한계·실패 사례를 함께 보고한다. 목표나 판정 기준을 결과 확인 뒤 바꾸지 않는다.

이 평가는 계획서 보강의 초기 효과를 확인하는 절차다. 실제 제출·평가 결과를 추적하기 전에는 반려율 감소가 입증됐다고 말하지 않는다. 현재 위험 추출/적중 지표와 이번 원본·보강본 평가를 혼합하지 않는다.

## 10. 후속 기획: 구현 가능성 제시와 실행 검증

2026-10-01 대표의 반영·흐름 통합 지시로 구현 경로·선행 조건·최소 검증안을 추가했다. `수정 확정·검증` 한 번으로 문안 검토와 구현 조건 점검을 수행하고, 제공 자료와 구체적 실행 승인이 있는 경우 최소 실행 검증도 같은 작업에 포함한다. 핵심 가정 1개·최소 검증 과제 1건·자동 재실험 0회로 결과를 반환한다. 자료 부족·미실행은 문안 검토 결과를 막지 않으며 구현 제안·준비 상태·실제 실행 관측을 구분한다. 본문을 자동 반영하거나 필수 두 번째 확정을 추가하지 않는다. 상세는 [FEASIBILITY_VALIDATION_PLAN.md](FEASIBILITY_VALIDATION_PLAN.md)를 따른다. 문안 검토 1회·자동 재수정 0회와 구현 예정 상태는 유지한다.
