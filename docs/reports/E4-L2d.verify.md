## 고칠 것

**공개 전 필수**

1. **본문 파서 불일치(L2c 미해결, 높음) + jobs 핸들러 글자 상한.** `serving.py`가 `json.loads(body.decode("utf-8"))`로 읽고 FastAPI는 `json.loads(bytes)`로 읽어, BOM·UTF-16 본문이면 미들웨어가 `plan_text`를 못 읽고 입장 관문을 건너뛴다. L2c 검증의 수정안 (a)~(d)를 그대로 적용해야 한다(bytes로 파싱, 못 읽으면 fail-closed 거절, `Serving.run`의 `force=True`·무예약 실행 재검사, BOM/UTF-16/UTF-32 테스트). jobs에는 재입장이 있어 차단·속도·예산·대기열은 막히지만, **`create_job` 핸들러가 `len(req.plan_text) > srv.config.max_plan_chars`를 직접 거절하지 않아 12만 자가 202**(pydantic 상한 20만 자까지). 한 줄(413) 추가. 동기 경로는 미들웨어 수정 전까지 전면 우회(차단 ON에서 200).
2. **작업 저장소 고갈·결과 밀어내기(L2d 신규, 높음).** 합류·캐시 적중은 속도 제한·예산·대기열을 안 쓰는데(L2c 설계) 그 요청도 작업 슬롯(`NEUMANN_JOB_MAX` 200)을 하나씩 먹는다.
   - **재현 A(합류 홍수)**: 공격자가 새 계획서 1건을 시작(분석 1회)하고 같은 계획서를 **한 IP에서 230번 POST → 0.42초에 199건 202**(속도 제한 카운터 0, 429 없음). 저장소가 미완 작업 200개로 차서 **다른 IP의 정상 사용자 새 분석이 503 `busy` "지금 보관 중인 분석 작업이 많습니다"**. 분석이 끝날 때까지(약 60~70초) 지속, 공격자는 분당 분석 1건(속도 제한 안)으로 반복 가능 → 사실상 서비스 거부. L2c에서는 대기열 20을 채우려면 분석 20건이 필요했는데 jobs로 1건이면 된다.
   - **재현 B(결과 밀어내기)**: 캐시된 계획서를 한 IP에서 300번 POST → **1.64초에 300건 전부 202(183건/초, 한도 60/분 무시)**. 그 사이 **다른 사용자의 완료 작업이 404**로 사라짐(폴링 1.5초 간격보다 훨씬 빨리 200개가 밀려남).
   - 수정 방향: IP별 보관 작업 수 상한(예: 미완 5·전체 20)과 합류·캐시 적중 POST에도 IP별 보조 속도 제한, `_make_room`이 다른 IP의 끝난 결과를 밀어내지 않기(자기 IP 것부터), 캐시 적중은 저장소를 거치지 않고 짧은 보관.
3. **긴 토큰 한 개로 서버 전체 정지(신규, 높음~중간; L2c·E0b 교차).** `models.EMAIL_RE`(`[A-Za-z0-9._%+\-]+@…`)가 `@` 없는 긴 연속 문자열에서 O(n²)라 `plan_key`(미들웨어가 이벤트 루프에서 동기로 호출)가 **4만 9천 자 한 토큰에 1.75~1.94초, 12만 자 9.8초, 20만 자 33.9초**. 실측: 한 요청 동안 다른 사용자 `/health` 최대 **1.88초** 정지. **속도 제한이 이미 429를 내는 IP도 건당 약 1.5초씩 루프를 태운다**(429 4건 총 6.0초, `/health` 최대 2.95초) — plan_key가 속도 제한보다 앞이기 때문이다. 현실적인 계획서 텍스트는 0.02초라 정상 사용자는 영향이 없고, 공격자만 한 연결로 서버를 계속 얼릴 수 있다(고칠 것 1의 BOM으로 20만 자면 34초). 파이프라인 안의 `PlanDocument.from_text`도 같은 정규식이라 스레드에서 돌아도 GIL을 잡는다. 수정: 정규식을 선형으로(예: 앞에 `(?<![A-Za-z0-9._%+\-])` 룩비하인드 추가 또는 `@` 위치 먼저 찾기 — `models.py`는 계약 파일이라 PM·E0b 결정), 그리고 입장 전 값싼 검사(공백 없는 연속 문자열이 수백 자를 넘으면 거절)를 둔다. 정규식 수정 전까지 완화책은 글자 상한을 낮추는 것뿐이다.
