## 공개 인터페이스 (E3·E4·E5용)

```python
from neumann.index.search import search, SearchHit, last_search_status, warmup, set_query_embedder
from neumann.index.store import get_excerpts, get_work, get_reviews, get_excerpt, get_rule_tags, get_source_text
from neumann.index.store import IndexStore, set_store, build_store_from
from neumann.index.taxonomy import tag_excerpts, classify
from neumann.index.sentences import split_sentences, excerpts_for_review

search(queries: list[str], k: int = 10, exclude_work_ids: set[str] | None = None,
       *, store=None, alpha=None, score_floor=None) -> list[SearchHit]
SearchHit(work_id: str, score: float, dense: float, lexical: float, matched_query: str)  # 모두 0~1, NeumannModel
get_excerpts(work_id) -> list[Excerpt]     # 심사평 순서(작성 시각→review_id) → 원문 위치. 없는 논문은 []
get_work(work_id) -> Work                  # 없으면 KeyError
get_reviews(work_id) -> list[ReviewEvent]  # 없으면 []
get_excerpt(excerpt_id) -> Excerpt | None
get_rule_tags(work_id) -> list[RiskTag]    # 빌드 때 계산한 규칙 태그(generator=rule)
get_source_text(source_id) -> str | None   # E5 check_result(result, source_lookup=get_source_text)
tag_excerpts(excerpts) -> list[RiskTag]    # 비상 경로: 즉석 규칙 태깅
```

- 점수: 질의마다 `score = 0.6·dense + 0.4·lexical`, 논문 점수는 질의 중 최댓값, 그 질의가 `matched_query`. 정렬은 점수 내림차순, 같으면 work_id(결정적).
- `lexical`은 `BM25 / Σ idf(질의 낱말)`을 1에서 자른 값이다(질의 최댓값 정규화가 아니다 — 무관한 질의의 1등이 1.0이 되지 않게). 한국어 낱말은 코퍼스에 없어 분모에만 들어가므로 한국어 질의의 lexical은 0에 가깝고 dense가 찾는다.
- 강등: 모델 경로가 없거나 차원·모델이 색인과 다르면 어휘 검색만 하고 `last_search_status()`에 `backend="lexical_only", degraded=True, reason=...`. E3는 이 값을 `StageStatus`에 옮겨 적으면 된다.
- 서버(E4): 시작 때 `warmup()`을 부르면 색인 로드(약 1.1~1.6초) + bge-m3 로드(10~16초)를 미리 한다. 이후 질의 1건 20~30ms(첫 질의 CUDA 예열 약 0.3~0.5초).

## 결정 (스펙이 모호해서 고른 것)

1. **색인은 자기완결 스냅숏이다.** `data/index/`에 works·reviews를 함께 저장한다. 오프셋은 정확히 그 심사평 문자열에만 유효하므로, E1이 코퍼스를 다시 만들어도 색인과 원문이 어긋나지 않게 했다. 입력 해시(`works.jsonl`·`reviews.jsonl` sha256)는 manifest `input`에 있다.
2. **절 제목도 문장으로 둔다**("Summary:", "Strengths:", "Weaknesses:", "Questions:", "Meta Review:" 약 18,000개). astra가 문장 번호를 볼 때 극성 맥락(장점 절인지 약점 절인지)을 알 수 있게. 규칙 태거도 이 제목을 따라 극성을 정한다. 인용 근거로는 쓰일 일이 없다(태그가 붙지 않음).
3. **SearchHit은 `NeumannModel`**(pydantic, extra=forbid, `model_dump` 가능)이고 필드는 스펙의 5개뿐이다. 추가 인자(`store`, `alpha`, `score_floor`)는 키워드 전용이라 E3 호출 모양과 충돌하지 않는다.
4. **어휘 점수 정규화**는 질의 최댓값이 아니라 질의 idf 합(OOV 포함)으로 나눈다(위 설명). 점수가 절대 척도에 가까워져 L1의 하한 보정이 쉬워진다.
5. **임베딩 모델을 못 읽으면 예외 대신 어휘 검색으로 강등**하고 `last_search_status()`·로그에 남긴다. 빌드도 같은 경우 `--no-embed`처럼 만들고 manifest `backend.degraded=true`.
6. **excerpt 순서**는 E1 `reviews_for`와 같은 기준(작성 시각 → review_id) → 원문 위치.
7. 긴 문장(800자 초과)은 `;`에서 한 번 더 나눈다. 그래도 800자 넘는 문장이 56개 남는다(대부분 참고문헌 목록).
8. `load_corpus`가 이 브랜치에 없어서 `--source processed`(기본)는 import 실패 시 같은 폴더의 jsonl을 계약 모델로 직접 읽고 manifest에 `input.fallback`으로 적는다. `--source jsonl`·`--source fixtures`도 있다.
9. 과제 파일과 계획서의 차이는 없었다. 계획서 §4 E2의 "축별(method/data/evaluation) 색인"은 L1 범위라 L0에서는 논문당 벡터 1개(제목+초록)다.

## 못 한 것

- **E1 `load_corpus` 경로로 실제 빌드는 못 했다**(아직 main에 없음). E1 worktree의 `Corpus` 모양(works는 dict, reviews는 list)에 맞춘 어댑터와 테스트는 있다. E1 병합 뒤 `python scripts/build_index.py`를 한 번 다시 돌리면 manifest `input.source`가 `processed`가 된다(내용은 같은 파일이라 문장 수도 같아야 한다).
- 점수 하한·가중치 보정, 축별 색인, 문장 단위 보조 색인 — L1.
- 규칙 태거 정밀도는 재지 않았다(다듬지 않는다는 과제 지시). DISAPERE 골드 대비 측정은 E5-L1 채점기로 할 수 있다.
- 규칙 태깅이 빌드에서 가장 느리다(24~30초, 13만 문장 × 정규식 약 90개). 필요하면 L1에서 사전 필터로 줄인다.
