## 무엇을 했나

`src/neumann/sources/retraction.py` 하나에 다음을 넣었다.

| 기능 | 내용 |
|---|---|
| `build(csv_path, data_dir)` | CSV → 공유 데이터 폴더 `data/processed/`에 `retraction.jsonl`(PostStatus 한 줄씩), `retraction_facets.json`(분야 prior용 패싯), `retraction_manifest.json`(건수·kind 분포·sha256·소요 시간·코퍼스 조인) |
| `get_post_status(doi) -> list[PostStatus]` | **원논문 DOI** 기준 조회. 입력은 정규화 전 문자열도 된다(대소문자, `https://doi.org/`, `doi:`). 공지 DOI로는 찾지 않는다(방향 함정). 없으면 `[]` |
| `field_failure_prior(subject_keywords) -> dict` | RW `Subject`(130종)와 키워드를 단어 경계로 맞춰, 그 분야 철회·우려표명 레코드의 사유 빈도와 R9 하위코드 빈도(전체 대비 기준선·lift 포함) |
| `join_corpus(data_dir)` | `processed/*.jsonl` 중 Work 모양 파일을 찾아 DOI로 조인. 코퍼스가 없으면 `corpus_missing` |
| CLI | `python -m neumann.sources.retraction build / join / lookup DOI / prior KW…` |

신원: `Author`·`Institution`·`Country`는 읽자마자 버린다. `Title`·`URLS`·`Notes`도 저장하지 않는다(`Notes`에 사람 이름·외부 링크가 섞인다). 행 해시(`provenance.content_sha256`)는 원본 행 전체의 sha256이라 원문 대조는 되지만 값은 드러나지 않는다.

### 1. 건수·kind 분포·DOI 정규화 규칙

명령:

```

```

출력(요약, 전체는 `data/processed/retraction_manifest.json`):

```

"records_written": 66737,
"skipped": {"blank_rows": 0, "unknown_nature": 0, "no_target_doi": 5947},
"kind_distribution_all_rows": {"correction": 1535, "expression_of_concern": 3724, "reinstatement": 161, "retraction": 67264},
"kind_distribution_written":  {"correction": 1504, "expression_of_concern": 3695, "reinstatement": 156, "retraction": 61382},

"outputs": {"retraction.jsonl": {"bytes": 52119723, "sha256": "e93d4f82…0944", "lines": 66737},
            "retraction_facets.json": {"bytes": 2695997, "sha256": "1158502a…8078"}},
"elapsed_s": 3.186
```

- 두 번 돌려 출력 sha256이 같다(jsonl `e93d4f82…0944`, facets `1158502a…8078` 두 번 동일).
- 사전 실측(`retraction.md`, 2026-09-11 스냅샷 72,293행)보다 391행 늘었다. 사유 라벨 112종, Subject 130종은 같다. 이번 파일에는 공백행이 없다(사전 실측 때는 201행).
- kind 매핑: `Retraction→retraction`, `Expression of concern→expression_of_concern`, `Correction→correction`, `Reinstatement→reinstatement`. 모르는 값은 저장하지 않고 `unknown_nature_values`에 센다(이번 0).
- **DOI 정규화 규칙**(`normalize_doi`, 저장·조회·조인 모두 같은 함수): 앞뒤 공백 제거 → `https://doi.org/`·`http://dx.doi.org/`·`doi:` 접두 제거 → `%XX` 퍼센트 인코딩 해제(RW에 `%3C…%3E`로 적힌 SICI DOI가 있어서) → 소문자 → `^10\.\d{4,9}/\S+$`가 아니면 None. `unavailable`·빈 값·`xx10.1007/…` 같은 오기(2건)는 None. `models.Work.doi` 검증기(URL 접두 제거 + 소문자)와 같은 결과를 내는지 테스트로 확인했다.
- 근거 링크: `url = https://doi.org/{notice_doi}`. `<`·`>`·`#`·`%`는 퍼센트 인코딩한다.

## 결정 (스펙이 모호해서 고른 것)

1. **계약에 없는 RW 필드**: `PostStatus`에 `rw_record_id`·`reason_categories`·날짜·분야 칸이 없고 `extra="forbid"`다. 계약은 바꾸지 않고, Record ID는 `post_status_id = "rw:{Record ID}"`로 싣고, 분야·사유 집계는 별도 파일 `retraction_facets.json`에 둔다.
2. **원논문 DOI가 없는 5,947행**은 PostStatus로 쓰지 않는다(계약상 `work_id`나 `target_doi`가 있어야 하고, 가짜 `work_id`를 만들면 Work가 있는 것처럼 보인다). 대신 패싯에는 넣어 분야 prior에는 센다(`facet_records` 72,684).
3. **kind**는 RW `RetractionNature` 4종만 옮긴다. `partial_retraction`·`withdrawal`·`removal`은 RW가 구분하지 않으므로 사유 코드로 추정하지 않는다.
4. **사유 → 위험코드**는 기획 키트 `03_risk_taxonomy` §7 표를 그대로 옮겼다(31개 → R9.1~R9.9). 절차 코드 20개도 §7 그대로이며, 그중 18개가 현재 CSV에 있다(`Transfer of Article`, `Withdrawal`은 없음). 나머지 63개 라벨은 위험코드 없이 사유 빈도에만 나온다. `02_data_schema` §4.4의 13분류(`PROCESS_ONLY` 등)와 `CITATION_MANIP→R6.5`는 매핑 정의 파일이 키트에 없어 만들지 않았다. 그래서 CS 상위 사유인 `Concerns/Issues about Referencing/Attributions`(0.441)는 `risk_code: null`이다.
5. **분야 prior 단위**: 해당 분야 레코드 중 그 사유를 1번 이상 가진 비율(레코드 단위, 여러 분야에 걸린 레코드는 1번). 기본 kind는 철회+우려표명(정정은 사유 커버리지가 낮고 재게재는 반대 신호), 인자로 바꿀 수 있다. 절차 코드는 기본 제외. 키워드가 어느 Subject에도 안 맞으면 전체 분포로 슬쩍 대체하지 않고 `status: "no_match"`를 돌려준다.
6. **accessed_at**: 로컬 CSV 파일 수정 시각(반입 시각, 2026-09-28T10:26:14Z)을 쓴다. 빌드 시각을 쓰면 출력 해시가 매번 바뀐다. 배포판 생성일(2026-09-25)은 `provenance.api_version = "rw-csv:2026-09-25"`와 manifest에 따로 적는다. `provenance.source_url`은 데이터셋 원본 URL(GitLab raw CSV)이다. RW 레코드별 공개 URL은 없다.
7. **PostStatus.text**는 비운다. RW에는 공지 본문이 없고 `Notes`는 대부분 PubPeer 링크라 근거 문장이 아니다. 근거는 "사유 통제어휘 + 공지 DOI 링크"다(`retraction.md` §7-3).
8. 실행 진입점은 `scripts/collect_retraction.py` 대신 모듈 CLI(`python -m neumann.sources.retraction`)로 했다. 이 과제의 소유가 `retraction.py`와 테스트뿐이어서다.
9. 테스트 픽스처는 `tests/fixtures/`(PM 소유)가 아니라 테스트 파일 안에 문자열로 넣었다.

## 못 한 것

- Crossref REST `GET /works/{doi}`의 `updated-by[]`로 하는 런타임 보강(RW에 없는 출판사 단독 정정·철회, 최신성)은 만들지 않았다. 네트워크 호출이 없고 로컬 CSV만 쓴다.
- 13분류(`reason_categories`)와 `PROCESS_ONLY`만 가진 레코드를 저장하지 않는 규칙(02_data_schema §3.5)은 계약에 칸이 없어 적용하지 않았다. 절차 코드는 prior 단계에서 뺀다.
- 공지일·원논문 게재일(게재→철회 지연)은 계약에 칸이 없어 저장하지 않았다.
- 코퍼스(ICLR)에 DOI가 없어 실제 매칭은 0건이다. 제목·arXiv id로 매칭하려면 별도 과제가 필요하다(제목 완전 일치도 0건이었다).

## 제안 (계약)
