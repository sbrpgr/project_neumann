## 방법

**지연 모델(기본값, `--delay task=최소:최대`·`--delay-scale`로 바꿈).** 과제마다 균등 분포 지연을 `time.sleep`으로 넣는다(GIL을 놓는다 — 실제 HTTP 대기와 같은 성질).

| 과제 | 호출 수/건(측정) | 지연(초) | 근거 |
|---|---|---|---|
| fitness | 1 | 4~6 | E3-L1c 라이브 5~7초 |
| query_axes | 1 | 2.5~3.5 | 지시(검색어 1회 약 3초) |
| extract_issues | 23~29묶음, 한 건 안에서 24개씩 병렬 | 2~5 | 지시(묶음마다 2~5초 × 약 30묶음 병렬) → 단계 약 5~8초 |
| synthesize_cards | 1 | 9~11 | 지시(약 10초) |
| expected_review | 1 | 9~11 | E3-L1a 라이브 12.5초 |
| checklist | 1~2(카드 수, 3개까지 병렬) | 9~11 | E3-L1b 라이브 16.4초 |
| semantic_validate | 1~2 | 9~11 | E3-L1b 라이브 12.4초 |

→ 건별 합계 52~57초(측정). E5-L0e2e 라이브(61~69초, 당시 v1 단계 없음)와 같은 규모다.

**계획서.** 기반 10건: 데모 3(`tests/fixtures/plans/plan*.md`) + 채운 예시 2(`templates/examples`) + 템플릿 골격 5. 사용자 k = 기반 k mod 10 + 끝에 한 줄 `부하 시험 변형 {N} 사용자 {k+1}번 메모.` → 요청마다 본문(plan_id)이 달라 어떤 캐시도 적중하지 않는다. 변형 줄은 한글·숫자만이라 검색어가 바뀌지 않는다(단위 시험으로 확인). 서로 다른 본문 33개(본 측정)·88개(추가 측정).

**기준 지문.** 라운드 전에 모든 본문을 지연 0으로 순차 실행해 지문(유사 연구 id·점수, 카드 유형·근거 id, 체크리스트 수, 단계 상태)을 만든다. 동시 실행 결과와 비교한다(모두 결정적이라 같아야 한다). 이 순차 실행이 색인·발췌 캐시 예열도 겸한다(공개 서버도 E4-L2c 예열을 한다). 서버 기준 33개와 직접 호출 기준 33개도 서로 대조했다: **불일치 0/33**.

**측정.** 건별 총 시간(서버 모드는 클라이언트 왕복, 세마포어 대기 = 왕복 − 파이프라인 실행), 단계별 시간(`manifest.timings_s`, 검색 단계는 임베딩 락 대기 포함), 임베딩 락 대기(요청별), 처리량 = N ÷ 전체 시간 × 60, nvidia-smi GPU 전체 메모리 최대(1초 폴링, 라운드 전 기준값과 차이), 파이프라인 프로세스의 작업 집합 최대·수명 최대·전용 커밋(추가 측정부터), CPU(프로세스 CPU 시간 ÷ 경과 = 코어 수 환산, 0.5초 창 최대), GIL 지연(5ms 잠들기 탐침의 초과 시간 p99·최대), 스레드 최대, 오류·예외·단계 error·새 강등, 검색 상태 섞임(아래 제안 1).

**안전장치.** `NEUMANN_LLM_PROVIDER=mock`이 없으면 시작하지 않는다. `OpenAIProvider.complete_json`을 예외로 바꿔 둔다. 이 프로세스와 서버 자식 프로세스 환경에서 `OPENAI_API_KEY`를 뺀다. 서버 쪽 `make_llm`은 지연 mock만 돌려준다.

### OpenAI 한계(이 시험이 재지 않은 것)

- 실제 OpenAI 지연 분포, 동시 요청 때 느려짐, 429(속도 제한)·5xx, 분당 토큰(TPM)·분당 요청(RPM) 한도는 **측정하지 않았다**(대표 지시로 호출 0회). mock 지연은 고정 분포라 실제 꼬리 지연(수십 초)이 없다.
- 분석 1건이 보내는 양(mock 호출에서 센 값): LLM 호출 **29~43회**, 입력 **25만~41만 자(평균 32.5만 자)**(원자료 범위, 검증 정정). 대부분 심사평 영어 문장이라 글자 ÷ 4로 잡으면 **약 8만 입력 토큰/건**(거친 추정, 토크나이저로 세지 않음). 출력·추론 토큰은 따로 든다.
- 그래서 동시 N건이 계속 돌면 입력만 약 **N × 9만 토큰/분**(8만 × 60/55), 요청 약 **N × 38회/분**이 필요하다. 동시 6 → 입력 약 0.53M TPM(출력 여유 1.3배 포함 약 0.7M), 동시 12 → 입력 약 1.06M TPM(약 1.4M). 게다가 지적 추출은 한 건 안에서 묶음 24개를 한꺼번에 보내므로 동시 N이면 순간 동시 요청이 최대 N × 24개다.
- **OpenAI 한도가 이보다 낮으면 실제 상한은 로컬 측정보다 낮다.** 한도를 넘으면 `OpenAIProvider`가 429를 한 번 다시 시도하고(호출 상한의 절반 안에서), 그래도 실패한 묶음·단계는 규칙 비상 경로로 떨어져 결과가 강등(degraded)된다 — 서버가 죽지는 않지만 품질이 떨어진다. PM이 OpenAI 대시보드에서 제품 모델(설정 `NEUMANN_LLM_MODEL`)의 TPM·RPM을 확인하고 `N ≤ TPM 한도 ÷ 12만`(입력 9만 × 출력 여유 1.3), `N ≤ RPM 한도 ÷ 38`로 맞추기를 권한다.
- cloudflared 약 100초 응답 끊김은 E4-L2d 작업 API(폴링)가 푼다. 대기열이 길면 대기 시간은 `(순번 ÷ N) × 55초`다.

## 제안(코드 수정은 소유 밖이라 하지 않음)

1. **(E2) 검색 상태를 전역 변수로 두지 않기.** `neumann.index.search`의 `_STATUS`(`last_search_status()`)는 프로세스 전역이고, 파이프라인은 `backend.search()` 뒤에 `backend.status()`로 그것을 읽는다. 두 요청의 검색이 거의 동시에 끝나면 `plan_checks.search.backend_status`(n_hits·top_score·elapsed_s·degraded)에 **다른 요청의 값**이 실릴 수 있다. 이번 측정에서는 한 번도 관찰되지 않았다(검색 상태 섞임 0, 계산만 N=12 포함 — 임베딩 락과 LLM 지연이 검색 시점을 흩어 놓아서다). 검사기(`search_status_mixup`)는 단위 시험으로 동작을 확인했다. 고치는 법: `search()`가 상태를 결과와 함께 돌려주거나(예: `search(..., return_status=True)`), `contextvars`/스레드 로컬에 둔다. `degraded` 판정이 남의 상태로 바뀌면 단계 강등 표시가 틀릴 수 있어 공개 전에 고치는 것이 좋다.
2. **(E3) 지적 추출 병렬을 서버 전체 상한으로.** `NEUMANN_EXTRACT_PARALLEL`(기본 24)은 분석 한 건 안의 상한이라 동시 N이면 OpenAI 동시 요청이 N × 24개까지 간다. 프로세스 공용 세마포어(예: 전체 48)를 두면 동시 수를 올려도 OpenAI 순간 요청과 429가 늘지 않는다. 당장은 `NEUMANN_MAX_CONCURRENT`를 올릴 때 `NEUMANN_EXTRACT_PARALLEL`을 `48 ÷ N` 근처로 낮추는 것으로 대신할 수 있다(추출 단계가 조금 길어진다).
3. **(E2) 임베딩 락은 유지.** 위 encode 표대로 락 쪽이 안전하고 빠르다. 여러 요청의 검색어를 한 번에 묶어 encode하는 배치는 락 대기가 최대 0.2초라 지금은 이득이 없다.
4. **(PM) E4-L2c·E4-L2d 병합 때 `NEUMANN_MAX_CONCURRENT` 공개값 결정.** main의 `MAX_CONCURRENT = 2` 상수는 E4-L2c 패치가 지운다. anyio 스레드 풀 기본 40개가 동기 파이프라인의 실제 동시 실행 상한이다(`run_in_threadpool`). 동시 상한을 40보다 크게 하려면 `anyio.to_thread.current_default_thread_limiter().total_tokens`를 시작 때 올려야 한다(측정: 48로 열어도 40만 돌았다). 공개 권장값(6)에서는 해당 없음.

## 한계

- 실제 OpenAI를 부르지 않았다(위 절). mock 응답은 규칙 결과라 카드 수(1~6장)·체크리스트 호출 수가 실제와 다를 수 있다.
- 결과 캐시·합류·대기열(E4-L2c)·작업 API(E4-L2d)는 main에 없어 **이 시험의 서버는 main 앱 그대로**다(동시 상한만 바꿈). 서빙 층의 오버헤드는 E4-L2c·L2d 보고서의 가짜 파이프라인 시험을 따른다.
- 한 번에 N명이 같은 순간 누르는 폭주(burst) 한 번씩만 쟀다. 오래 계속되는 부하(수 시간, 메모리 누적)는 재지 않았다. 발췌 pydantic 캐시(`IndexStore._excerpts`)는 처음 보는 논문마다 커지므로 오래 돌면 작업 집합이 는다(상한은 코퍼스 크기).
- 시스템 전체 CPU·GPU 사용률은 이 PC의 다른 작업이 섞인 값이다. 판단은 프로세스 단위 값(CPU 시간, torch 할당)으로 했다. 측정 시작 때 GPU는 비어 있었다(0MiB, 계산 프로세스 없음).
- 토큰 수는 글자 ÷ 4의 거친 추정이다.
- 건별 합계 약 55초는 지시값(약 60초)에 맞춘 것이다. E5-L0e2e 라이브(61~69초)는 v1 단계(적합성·예상 심사평·체크리스트·2차 검증) 전 측정이라, 지금 파이프라인의 실제 라이브는 더 길 수 있다(각 단계 라이브 보고서 값을 더하면 약 100초 안팎). 대기는 `sleep`이라 건별 시간이 길어져도 로컬 자원 결과(동시 수별 GPU·RAM·스레드)는 같다. 다만 같은 처리량에 필요한 동시 수는 늘고, 동시 한 자리가 쓰는 분당 토큰은 그만큼 준다(공식의 60/55를 60/실제 초로 바꾼다).

## 결정(스펙이 모호해서 고른 것)

1. **v1 단계(적합성·예상 심사평·체크리스트·2차 검증) 지연도 넣었다.** 지시의 세 과제(검색어·추출·합성)만으로는 합계가 약 20초라 "합계 약 60초"와 맞지 않는다. 각 단계 라이브 보고서 값 근처(5·10·10·10초)로 채웠다.
2. **서버 모드 엔드포인트는 `/premortem/view`**(화면이 쓰는 경로, 응답 JSON 만들기 포함). 지문은 서버 쪽 파이프라인 결과에서 계산해 `/_loadtest/stats`로 받는다.
3. **서버 동시 상한은 max(N)로 고정**(본 측정 12, 추가 48)해서 세마포어가 측정을 막지 않게 했다. 대기 열이 0.05초 이하인 것으로 확인.
4. **서버 모드를 먼저 돌린다.** 부하 스크립트 프로세스가 CUDA를 올리기 전에 재야 nvidia-smi 값이 서버 몫만이다.
5. **폭주 한 번 = 라운드.** 처리량은 N ÷ 전체 시간. 1건 55초라 라운드마다 약 1분.
6. 권장값은 로컬 여유를 크게 두고(본 측정 12의 절반), OpenAI 한도 공식을 같이 적었다. 로컬만 보면 12~24도 되지만 OpenAI TPM(N=12면 약 1.06M/분 입력)이 먼저 막힐 가능성이 커서 6으로 잡았다.
