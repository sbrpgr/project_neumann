## 최종 판정: **PASS-조건부**

완료 기준 2개(형식별 추출·한국어 보존·크기·HWP 거부, verify.py)는 팁에서 직접 재현했고 통과한다. 디스크 미저장도 반증에 실패했다. 공개 서버 전제의 증폭 공격(압축 폭탄 docx, 페이지 증폭 pdf)은 `88e5aa2`에서 실제로 재현됐고 `31f0b88`에서 막힌 것을 확인했다.

**병합 전 고칠 것 (1건, 한 줄 수정)**

1. `upload.py` 606행 `MultipartParser(boundary, ...)` 생성이 `try` 밖이다. `Content-Type: multipart/form-data; boundary=` 뒤에 256자를 넘는 boundary를 보내면 `FormParserError`가 그대로 올라가 **500**이 된다(본문은 일반 문구 `Internal Server Error`라 내부 정보 노출은 없다). 생성 줄을 `try` 안으로 옮기면 400이 된다. 퍼징 6,600건 중 5xx는 이것 하나뿐이다.

**병합 뒤·공개 전에 처리할 것 (병합 조건 아님)**

2. `/upload/plan`에 속도 제한(PM이 이미 남긴 일: `serving.py` 보호 경로). 지금은 슬롯 2개를 느린 PDF 2건(각 90KB)이 20초씩 잡으면 그동안 **모든 업로드가 503**이다(txt·md도 슬롯을 쓴다). 시험 결과는 아래 4절.
3. 파일명 처리 보강: CP949 바이트 파일명이 latin-1로 읽혀 깨진다(본문은 정상). 응답 `filename`에 제어문자·HTML 조각이 그대로 에코된다(JSON 이스케이프만). 화면은 `textContent`로만 쓸 것.
4. 테스트 공백(아래 6절): 작업자 강제 종료 인자, `_worker_main`의 쓰기 차단 호출, 스트림 조기 중단, 작업자 예외 문구.
5. 화면 과제에 전달: 평문 txt·md는 10MB 이하여도 **정리 뒤 50,000자를 넘으면 413**이다(SEC-1 결정). 드롭존 문구가 "최대 10MB"만 말하면 사용자가 혼란스럽다. 목업의 HWP 문구는 빌더가 이미 전달했다.

| `_worker_main`의 `_deny_disk_writes()` 호출 제거 | 테스트는 함수만 직접 호출함 | 함수는 별도 프로세스에서 동작 확인, 호출 위치는 코드 확인(461행, 첫 문장) |
| 스트림 누적·Content-Length·파트 누적 검사 제거(각각·전부) | 마지막 크기 검사가 같은 상태코드를 냄 | 실제 서버에서 11.1MB 시점 413 확인 |
| HWPX mimetype 판별 제거 | `Contents/section` 이름 검사가 같은 결과를 냄 | HWPX 415 확인 |
| 작업자 `-I` 제거 | 테스트 없음 | 코드 확인 |
| 작업자 내부 예외 문구 노출 | 테스트 없음 | 오류 표본·퍼징에서 노출 0건 |

- 이전 커밋(88e5aa2): 유효 변이 17개 중 14개 잡힘. 살아남은 것은 DOCX 압축 해제 상한(100MB), PDF 쪽수 상한(300), HWPX mimetype 판별이고, 크기 조기 중단 3계층 변이도 전부 살아남았다. DOCX·PDF 상한은 팁에서 전용 테스트가 생겨 잡힌다.
- 파서라서 인용·LLM 표시 항목은 해당 없다. 빌더 보고서의 주장(43건→57건, verify 242건, 실문서 추출, SEC-1 재현 "127KB DOCX 37MB → 37초·24.8MB")은 내 측정과 일치했다(내 재현: 0.32MB → 121초, 0.15MB → 98.7MB 응답).

## 7. 정정·주의

- 빌더 보고서가 밝힌 대로 **작업자 메모리 상한은 없다**(Windows에 RLIMIT 없음). 20초·입력 10MB·zip 20MB·글자 상한으로 간접 제한된다. 이번 시험에서 작업자 메모리는 따로 재지 않았다(부모 피크만 잼: 팁의 폭탄 시험 부모 피크 51~173MB).
- 이 시험에서 "폭탄이 도는 동안 다른 라우트(/health)가 느려지는가"는 클라이언트 쪽 연결 비용(약 0.2초)과 구분되지 않아 결론을 내지 않았다. 증폭 피해의 근거는 CPU 시간·메모리·응답 크기다.
