## B2 — 내보내기 `expected_review.audit` 형태 (`src/neumann/api/export.py`)

### 원인
`_review_for_report`가 `dict(audit.get("dropped_reasons") or {})`, `for d in audit["dropped"]`, `str(d[0])`를 형태 확인 없이 불렀다.
`dropped_reasons`가 `1`·`[1]`·`1.5`이면 TypeError, `dropped`가 정수면 TypeError → 라우트가 ValueError만 422로 바꾸므로 **HTTP 500**.
`_gate_export_result`의 `int(audit.get("drop"))` 등도 같은 부류다. 또 모르는 audit 필드는 리포트 JSON에 그대로 실려
깊이 1,200단 중첩이면 `_json_md`의 `json.dumps`가 RecursionError → 500이었다.

### 정책(바꾼 것)
- audit 자체가 객체가 아니면 **422**(기존 정책·기존 테스트 유지).
- 알려진 필드만 형태를 확인해 싣는다: 개수(`gen·pass·drop·no_evidence·generated·passed`, 0~10⁹ 정수, bool 제외),
  짧은 문구(`gate·note·dropped_text` ≤500자), 사유 코드 맵(`dropped_reasons·reasons`, 코드 `[A-Za-z0-9_.:@-]{1,64}` → 개수, ≤64개),
  코드 목록(`no_evidence_reasons`, `dropped_keys`), `linked_rate`(None 또는 0~1 유한 수).
- 형태가 틀린 필드·모르는 필드는 **값을 버리고 이름만 `audit.dropped_keys`**에 남긴다(이름도 코드 글자·64자로 줄이고 개인정보 가림).
  README·리포트 "주의"에 "형식이 맞지 않거나 알 수 없는 필드 N개를 값 없이 제외" 한 줄. 내보내기는 계속된다(200).
- `dropped`의 `[사유 코드, 문장]` 쌍은 코드 모양일 때만 센다. 원문(`dropped`·`dropped_detail`)은 예전처럼 싣지 않는다.
- 요청 JSON 중첩이 **64단**을 넘으면 조립 전에 **422 `package_limits`**(`json_depth_exceeds`, 재귀 없는 스택 순회).
  서빙 미들웨어도 같은 `package_limit_refusal`을 부르므로 같은 판정. 정상 fixture 패키지 깊이는 6단.
- 서버 서명된 정상 결과(파이프라인 audit 모양)는 바뀌지 않는다: 값 보존·`dropped_keys` 없음·경고 없음·두 번 거쳐도 같은 모양(테스트).

### FAIL ① 승인 철회 뒤 재시도 상태 모순
- 원인: 첫 응답이 "쓸 수 있지만 2문장 초과"라 재시도하는데 그 사이 `NEUMANN_LIVE_LLM_OK`가 철회되면 `locked=True`인데
  `ok = final is not None`이 True로 남아 행 `status=ok`·위험 3개·`generator=none`이 동시에 나왔다.
- 수정: 잠김이 한 번이라도 있으면 사전 고정 재시도 절차를 끝내지 못한 것으로 보고 **`ok=False`·`output=None`·`model_actual=None`,
  캐시에 쓰지 않음**. 잠긴 시도는 `attempts[i].locked=True`, 잠기기 전 시도 수 `attempts_before_lock`, 행 메모
  "재시도 전 잠김, 앞 시도 n회 응답은 쓰지 않음". `riskset_from_entry`는 `locked`이면 기록의 ok와 무관하게 `status=error`·위험 0개
  (이전 버전이 남긴 모순 기록도 성공으로 읽지 않음).

### FAIL ② 캐시 키가 실효 모델과 다름
- 원인: 키를 `provider.model`(요청 모델)로 먼저 만들고, `generate`가 호출 직전 가드로 `self.model`을 Sol로 바꿨다.
  Astra 권한이 생성 뒤 철회되면 Astra 키에 Sol 결과가 쓰이고, 다음 실행은 Sol 키를 찾아 매번 다시 불렀다.
- 수정:
  - `effective_identity()`/`provider_identity()` = 지금 보낼 (provider, 가드 뒤 model, effort). `cache_key`는 이 값으로 만든다
    (식 `sha256(provider|model|effort|prompt_version|plan_id)`는 그대로라 기록이 맞는 옛 항목과 같은 키).
  - `generate`는 요청 모델 속성을 바꾸지 않고 호출마다 실효 모델을 계산해 보내며, 결과에 보낸 `model_requested`·`effort`를 적는다.
  - 조회 뒤 SDK 호출 직전에 모델이 바뀌면 **실제로 보낸 모델의 키**에 쓴다. 시도마다 모델이 달랐으면 쓰지 않고 실패
    (`effective_model_changed`).
  - 캐시 재사용은 기록이 실효 값과 모두 맞을 때만: `system·key·provider·model_requested·effort·prompt_version·plan_id`,
    잠김 아님, `model_actual`의 Astra 계열 여부가 실효 모델과 같음, 새 형식이면 시도별 `model_requested`도 같음.
    맞지 않거나 읽을 수 없는 파일은 재사용하지 않고 새로 불러 덮어쓰며 `stale_cache`에 사유를 남긴다.
- 기존 캐시(`data/eval/baseline_llm_cache`, 읽기만) 41건 판정: sol 5·mock 6은 자기 키에서 기록 일치 → 재사용(재호출 비용 0),
  astra 30은 Astra 키에만 있어 `NEUMANN_ALLOW_ASTRA=1`로 실효 모델이 Astra일 때만 재사용. 데이터 파일은 바꾸지 않았다.
