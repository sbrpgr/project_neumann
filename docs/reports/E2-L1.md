# E2-L1 보고서: 검색 보정(질의 결합·점수 하한·축별 가중치·한국어 질의)

- 브랜치: `task/E2-L1` (main f636fad 기준) · 빌더: Claude Opus 5.5 · 검증 예정: Sonnet 5.5
- 색인: 공유 `data/index/`를 **읽기만** 했다(재색인 없음). 실측 산출은 `data/index_exp_e2l1/`(`before.json`, `probe.json`, `after.json`, `after.txt`). 커밋하지 않음
- GPU: bge-m3는 실측 한 번 돌 때 한 프로세스에서 한 번만 올렸다(cuda fp16, 로드 9.5~15초). 질의 약 50개는 문자열당 한 번 임베딩(캐시 래퍼)했고, 끝나면 캐시와 CUDA 메모리를 해제했다. 전체 실행은 before 1회, probe 2회, after 3회, 모델 테스트 1회

## 무엇을 했나

| 파일 | 내용 |
|---|---|
| `src/neumann/index/search.py` | ① **여러 질의 결합**: `fusion="rrf"`(기본, 질의별 순위 융합 `Σ 축가중치/(60+순위)`) 또는 `"max"`(L0). `per_query_min`(기본 1) = 질의별 상위 할당(가중치 큰 질의부터 번갈아, **k의 절반까지**). ② **점수 하한**: (질의, 논문) 쌍마다 `관련도 = max(dense, score)`에 건다. 기본값은 임베딩 모델별 실측 보정(`FLOOR_CALIBRATION["bge-m3"] = 0.45`). 보정값이 없는 모델이나 어휘만 검색(강등)이면 0이다. 하한을 넘는 논문이 없으면 `[]`를 돌려주고, `last_search_status()["relevance"]`에 `verdict="unrelated"`와 근거(하한·출처·1위 관련도·여유·실측 요약)를 남긴다. ③ **축별 가중치**: `axes=[...]`(질의와 같은 길이)가 오면 `NEUMANN_SEARCH_AXIS_WEIGHTS`(기본 `topic=1,method=1,data=1,evaluation=0.5`)를 결합 기여에 곱한다. 결과에 `axis_scores` ④ **한국어 질의**: `a = 1 − (1−alpha)·coverage`(coverage는 질의 낱말 중 색인 어휘에 있는 것의 idf 비율). 한국어만 질의는 `score = dense`, 영어는 L0와 같다. ⑤ 상태에 질의별 요약(`per_query`: 축·가중치·coverage·alpha·1위·하한 통과 수·`n_best_match`·`n_ranked_in_results`)과 `unmatched_excludes`(색인에 없는 제외 id, E2-L0 검증 관찰 B)를 남긴다 |
| `src/neumann/index/queries.py` (새 파일) | 축 이름·별칭 정리(`normalize_axis`: method/방법/methods…). `plan_axis_queries(text)`는 모델 없이 마크다운 계획서를 절 제목으로 나눠 `[(전문, topic), (제목+목표, topic), (방법, method), (데이터, data), (평가, evaluation)]`을 만든다 |
| `src/neumann/index/settings.py` | 새 설정 키 5개. `NEUMANN_SEARCH_SCORE_FLOOR`의 기본을 0.0에서 비움(None, 모델별 보정)으로 바꿈 |
| `scripts/build_index_calibrate.py` (새 파일) | 실측 스크립트. 관련 18건·무관 9건의 원점수 분포, 데모 3건(전문, 전문+영어 축 질의, 절 나눔), 한 질의 독점 재현, 하한 훑기(0.38~0.50), L0 설정 회귀 확인. 표적 논문 순위(BatteryML, Atomic Transport)도 잰다. 영어 축 질의는 astra를 부르지 않고 **고정 예시 문자열**을 쓴다 |
| `tests/e2/test_e2_l1_search.py` (새 파일) | 17건(아래) |

- **하한을 `score`가 아닌 `max(dense, score)`에 거는 이유**(probe 실측): 영어 data 축 질의가 표적 두 편을 **1위·2위**로 찾는데, 결합 점수는 0.418·0.401이다(lexical 0.28·0.17이 dense 0.50·0.53을 끌어내림). `score`에 0.45를 걸면 이 질의는 0편이 되고 영어 질의 en_battery도 3편만 남았다(probe). BM25는 근거를 더할 수만 있고 임베딩이 찾은 것을 깎지 못하게 했다
- 한국어 적응 alpha가 없으면(L0) 한국어 관련 질의의 결합 점수는 0.29~0.39로 영어 무관 질의(0.29~0.30)와 겹친다. 그래서 L0 척도로는 한 하한으로 둘을 가를 수 없었다(E2-L0 검증 관찰 C)

### 회귀: L0 설정으로 되돌리면 전과 같은가

`fusion="max", adaptive_alpha=False, score_floor=0.0, per_query_min=0`으로 부르면 `before.json`과 **순서가 8/8 같다**(여러 질의 4건, 단일 질의 4건). 점수 차는 최대 1e-6(float32 반올림)이다.

## 결정 (스펙이 모호해서 고른 것)

1. **하한은 `score`가 아니라 `max(dense, score)`에 건다.** 근거는 위 "분리점과 하한 근거"에 있다. 정렬은 계속 `score`로 한다
2. **하한은 임베딩 모델별로 둔다**(코드 상수 `FLOOR_CALIBRATION`). 계획서 §4 E2 함정 "하한은 백엔드마다 다르다"를 따랐다. 가짜 임베더(테스트), 다른 모델, 어휘만 검색에는 bge-m3 보정값을 쓰지 않는다(0, `verdict="unknown"`). 그래서 기존 fixture 테스트와 강등 경로가 그대로다
3. **한국어 적응 alpha를 기본으로 켰다.** 단일 질의의 순위는 거의 그대로다(데모 전문 상위 10편 겹침 9/10·10/10·10/10, 영어는 같음). 점수만 언어 간에 비교할 수 있게 된다(짧은 5쌍의 한국어/영어 1위 비율 0.38~0.48 → 0.63~0.80). 부작용으로 **한국어 질의의 `score`가 L0보다 0.2 안팎 높게 나온다**(데모 전문 1위 0.370 → 0.567). E3가 `score`를 위험점수 유사도로 쓰면 값의 범위가 바뀐다
4. **여러 질의일 때 결과 순서는 `fused` 순이고 `score`는 내림차순이 아닐 수 있다.** `score`, `dense`, `lexical`, `matched_query`는 L0처럼 "그 논문에서 점수가 가장 높은 질의" 값으로 둔다(절대 척도, 하한과 같은 척도). 순위 기여는 `fused`와 `per_query[*].n_ranked_in_results`로 본다
5. **질의별 상위 할당은 k의 절반까지만 한다.** 질의 8개에 k=10이면 할당만으로 자리가 다 차서 여러 질의가 함께 가리키는 논문이 빠지기 때문이다
6. **evaluation 축 가중치는 0.5다.** 평가 문구(ROC-AUC, R2, MAE, 정확도…)는 분야와 무관하게 겹친다. 전(max)에는 데모 2 상위 4편이 모두 evaluation 질의가 끌어온 무관 논문이었다(PROTAC, 항체 설계 등). 영어 evaluation 질의는 데모 1에서 하한을 넘는 논문이 0편이었다
7. 하한 0일 때 관련도 0인 쌍은 결과에는 남지만(L0처럼 "다 나온다") 순위 융합과 할당에는 기여하지 않는다
8. 영어 축 질의는 astra 호출 없이 고정 예시 문자열(스크립트 `AXIS_QUERIES`)로 쟀다. 실제 astra가 만드는 질의로 바꾸면 수치가 달라질 수 있다

## 못 한 것

- **데모 1 표적 두 편이 상위 10편에 둘 다 들지는 않는다.** Atomic Transport는 94위에서 9위로 올랐지만 BatteryML은 171위에서 22위다(전문 단독은 109/92 → 83/95). 전문 질의(한국어)의 점수가 높아 대부분의 `matched_query`가 전문이다. BatteryML을 올리려면 E3가 데이터 축 질의를 더 구체적으로 만들거나 `per_query_min=2` 이상을 쓰면 된다. 기본값을 이 한 건에 맞추지는 않았다
- 계획서를 절로 나눠 넣는 방식(`plan_axis_queries`)만으로는 표적 순위가 좋아지지 않았다(131/105, 영어 축 질의를 더하면 60/34). 한국어 방법 절이 GNN 일반 논문으로 끌린다. 함수는 쓸 수 있게 두었지만 기본 경로에 넣지 않았다
- **축별 문서 색인**(논문의 방법·데이터·평가 문장을 따로 임베딩)은 재색인이 필요해서 하지 않았다(지시: 재색인 금지). 이번 축 가중치는 질의 쪽에서만 건다
- 관련/무관 세트는 27건으로 작다. 무관 쪽은 과학 밖 글뿐이다. "과학이지만 코퍼스 밖"(의료영상 제목 한 줄 같은 것)은 1건만 봤다
- `.env.example`에 새 키 이름 추가: PM 소유라 고치지 않았다(아래)

## 다른 모듈이 알아야 할 것 / 다음 과제에 넘길 것

- **E3(파이프라인)**: 호출 모양은 그대로다. 다만 **기본 하한 0.45 때문에 무관한 계획서는 `[]`가 돌아온다.** `last_search_status()["relevance"]`(`verdict`, `top_relevance`, `floor`, `margin`, `basis`)를 `StageStatus`나 `notices`에 옮기면 "관련 없음" 판정과 근거를 화면에 보일 수 있다. 축별 질의를 쓰려면 `search(queries, k, excl, axes=[None, "method", "data", "evaluation"])`로 부른다. 결과의 `axis_scores`는 `SimilarWork.axis_scores`에 그대로 넣을 수 있다. 계획서만 있으면 `neumann.index.queries.plan_axis_queries(text)`로 모델 없이 축 질의를 만들 수 있다. `score`를 유사도로 쓰면 한국어 질의 값이 L0보다 커졌다(결정 3)
- **E4(MCP 서버)**: `search([query], k=k, store=...)`는 그대로 동작한다. 무관한 질의에는 빈 목록을 돌려준다. 시작 때 `search_fn("warmup", 1)`도 빈 목록일 수 있지만 상태(`backend`)만 쓰므로 문제없다. 필요하면 `relevance`를 응답 상태에 실을 수 있다
- **E5(백테스트)**: `exclude_work_ids`는 여전히 완전 일치다. 이제 접두어 없는 id는 `last_search_status()["unmatched_excludes"]`와 `n_unmatched_excludes`에 보이니, 누출 탐지 검사에 쓰면 된다. 백테스트에서 L0 결과를 재현하려면 `fusion="max", adaptive_alpha=False, score_floor=0.0, per_query_min=0`으로 부른다
- **E2-L3(확대 색인 `data/index_l3/`)**: 하한 0.45는 1,128편 색인에서 잰 값이다. 2,128편 색인으로 바꾸면 `python scripts/build_index_calibrate.py --index data/index_l3 --label l3`로 다시 재고 표를 비교할 것
- **PM**: `.env.example`에 이름만 추가해 달라: `NEUMANN_SEARCH_FUSION`, `NEUMANN_SEARCH_RRF_K`, `NEUMANN_SEARCH_PER_QUERY_MIN`, `NEUMANN_SEARCH_AXIS_WEIGHTS`, `NEUMANN_SEARCH_ADAPTIVE_ALPHA`(그리고 E2-L0이 제안한 키). `NEUMANN_SEARCH_SCORE_FLOOR`는 비워 둬야 모델별 보정을 쓴다. `.env`에 0.0이 적혀 있으면 하한이 꺼진다. 새 패키지는 쓰지 않았다
